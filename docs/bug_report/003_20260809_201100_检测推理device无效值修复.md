# Bug 修复报告 #003

- **报告编号**：003
- **记录时间**：2026-08-09 20:11:00
- **问题标题**：检测/计数推理因 `device='auto'` 无效值始终失败 + 任务状态轮询 404
- **涉及模块**：`backend/core/detector.py`、`config/models.yaml`、`backend/api/detect_api.py`、`backend/api/counting_api.py`、`frontend/src/views/algo/Detect.vue`、`frontend/src/views/algo/ModelRegister.vue`
- **严重程度**：致命（检测与计数推理完全不可用，任务状态无法轮询）
- **状态**：已修复并验证

---

## 一、问题现象

算法模型注册成功后，使用已注册模型执行检测推理测试及 UAV 原始图片检测时，系统返回
`success: false`，提示 `"检测失败: Invalid CUDA 'device=auto' requested"`，推理无法启动。
同时，异步计数任务提交成功后，轮询任务状态端点始终返回 404，无法获取结果。

### 2.2 根因复现（直接 Python 测试）

从项目根目录执行：
```python
from ultralytics import YOLO
m = YOLO('models/yolo12s_sugarcane.pt')
r = m.predict(img, device='auto')  # ← ValueError!
```

**错误输出**：
```
ValueError: Invalid CUDA 'device=auto' requested. Use 'device=cpu' or pass valid
CUDA device(s) if available, i.e. 'device=0' or 'device=0,1,2,3' for Multi-GPU.
torch.cuda.is_available(): True
torch.cuda.device_count(): 0
```

### 2.3 根因定位

**主因**：`device: 'auto'`（字符串）在 ultralytics 8.4.60 中不是有效的 device 值。
`select_device('auto')` 不将 `'auto'` 识别为"自动选择"，而是尝试解析为 CUDA 设备——
当 CUDA 不可用或 device_count=0 时，直接抛出 ValueError，**不降级到 CPU**。

**对照实验**（同一进程、CUDA 可用时）：

| device 值 | 结果 | 实际使用设备 |
|-----------|------|-------------|
| `None` | ✅ 成功 | cuda:0（GPU） |
| `0` (int) | ✅ 成功 | cuda:0（GPU） |
| `'cpu'` | ✅ 成功 | cpu |
| **`'auto'`** | **❌ ValueError** | — |

结论：`'auto'` 字符串在 ultralytics 8.4.60 中**始终无效**（即使 CUDA 可用也失败）；
正确的自动选择值是 `None`（Python None / YAML null），由 ultralytics 内部实现
GPU 优先 + CPU 降级。

**次因**：前端 device 下拉选项 `'cuda:0'` 同样无效（ultralytics 期望 `0` 或 `'0'`，
非 `'cuda:0'`）。

**附带发现**：`detect_api.py` 和 `counting_api.py` 的任务状态/结果轮询端点存在
`if "error" in task:` 判断错误——每个任务字典都含 `"error": None` 键（初始值），
导致条件始终为 True，状态查询始终返回 404，无法获取异步任务结果。

### 2.4 数据流追踪

```
前端 Detect.vue: device='auto' (默认值, L84)
  → POST /api/detect (form: device=auto)
    → detect_api.py: _parse_params → params['device']='auto'
      → detector.py: device = params.get("device", cfg.get("device", "auto"))  # = 'auto'
        → engine.predict(..., device='auto', ...)
          → ultralytics select_device('auto')  ← ValueError!
```

`models.yaml` 中 4 个模型均配置 `device: auto`，前端 Detect.vue / ModelRegister.vue
默认值与选项也含 `'auto'` 和 `'cuda:0'`，形成全链路无效值传播。

## 三、解决方案

### 3.1 后端 detector.py — device 归一化 + GPU 降级（核心修复）

新增 `_normalize_device()` 静态方法，将所有 device 输入归一化为 ultralytics 可接受值：
- `None` / `''` / `'auto'` → `None`（自动选择：GPU 优先 + CPU 降级）
- `'cuda:0'` / `'cuda:1'` → `0` / `1`（int）
- `'cpu'` → `'cpu'`（原样保留）
- `'0'` / `0` → `0`（字符串数字转 int）

新增 `_is_cuda_error()` 判断异常是否与 CUDA 相关，在 GPU 推理失败时自动降级到 CPU 重试
（应对 CUDA device_count 间歇性为 0）。

```python
device = self._normalize_device(params.get("device", cfg.get("device")))
try:
    results = engine.predict(..., device=device, ...)
except Exception as exc:
    if device not in (None, "cpu") and self._is_cuda_error(exc):
        logger.warning("GPU 推理失败，降级到 CPU 重试：%s", exc)
        results = engine.predict(..., device="cpu", ...)
    else:
        raise
```

### 3.2 config/models.yaml — device: auto → device: null

4 个模型的 `device: auto` 改为 `device: null`（YAML null → Python None）。

### 3.3 前端 Detect.vue / ModelRegister.vue — device 选项修正

- 默认值 `'auto'` → `''`（空，表示自动）
- 选项 `'auto'` / `'cpu'` / `'cuda:0'` → `''`(自动 GPU 优先) / `'cpu'` / `'0'`(GPU)

### 3.4 任务状态轮询 bug 修复

`detect_api.py` 和 `counting_api.py` 共 4 处 `if "error" in task:` 改为
`if task.get("error"):`——检查 error 值是否为真，而非键是否存在。

### 3.5 测试图片补充

创建 `mock/` 目录并生成 `DJI_0001.jpg` 合成测试图（640×640 绿色农田 + 随机斑点），
用于验证检测/计数管线连通性。

## 五、经验教训

1. **框架参数值需验证**：`device='auto'` 看似合理，但在 ultralytics 8.4.60 中并非
   有效值。集成第三方框架时，应查阅其 `select_device` 源码确认有效输入，而非凭直觉
   使用 `'auto'`。正确的自动选择值是 `None`。
2. **归一化层应放在后端单点**：在前端、配置文件、API 多处都可能出现无效 device 值，
   在后端 detector.py 的 `_normalize_device()` 统一归一化，比逐处修改更健壮，且向后
   兼容旧值。
3. **GPU 降级是必要的**：本机 CUDA device_count 间歇性为 0（~20 个桌面应用 GPU 竞争），
   `device=None` 虽能自动选择，但显式 `device=0` 在 device_count=0 时会失败。增加
   GPU→CPU 降级重试逻辑，确保推理在 CUDA 不稳定时仍能完成。
4. **`if key in dict` vs `if dict.get(key)` 的陷阱**：任务状态轮询的 404 bug 根因是
   `if "error" in task:` 检查键存在而非值——每个任务字典都含 `"error": None` 键，导致
   条件恒为 True。应使用 `if task.get("error"):` 检查值是否为真。

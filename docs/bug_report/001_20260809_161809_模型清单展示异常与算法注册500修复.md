# Bug 修复报告 #001

- **报告编号**：001
- **记录时间**：2026-08-09 16:18:09
- **问题标题**：模型清单展示异常 + 算法注册返回 500 Internal Server Error
- **涉及模块**：后端引擎初始化（`backend/core/engine.py`、`backend/api/batches_api.py`、`backend/api/processing_api.py`、`backend/api/health_api.py`）
- **严重程度**：高（前端两个核心功能完全不可用）
- **状态**：已修复并验证

---

## 一、问题现象

在成功启动前端应用和后端服务后，算法注册/模型管理功能出现两个持续存在的缺陷：

1. **模型清单展示异常**：`config/models.yaml` 中已完整定义的 4 个模型（yolov5su / yolov8s / yolo11s / yolo12s 甘蔗幼苗）未能在前端「算法管理」界面正确显示。
2. **算法注册失败**：通过系统界面新增注册算法时，操作失败，返回 **500 Internal Server Error**，前端提示「注册不成功」。

## 二、排查过程

### 2.1 数据流梳理

前端「算法管理」页面的数据链路如下：

```
Models.vue (onMounted → modelStore.fetchModels)
  → store/model.ts: modelsApi.list()
    → api/models.ts: client.get('/models')        [axios baseURL=/api]
      → Vite 代理 /api → Flask:5000
        → backend/api/models_api.py  GET /api/models
          → core.engine.get_registry()            ← 关键依赖
            → core/registry.load_from_yaml()      [读 models.yaml]
```

注册链路：`ModelRegister.vue → store.registerModel → POST /api/models/load → registry.register(config)`

### 2.2 实际复现

直接运行后端 `python -m backend.app`，进程在 import 阶段即崩溃：

```
File "backend/app.py", line 17, in <module>
    from api.health_api import health_bp
  File "backend/api/health_api.py", line 4, in <module>
    from core.engine import get_registry
  File "backend/core/engine.py", line 7, in <module>
    from core.detector import DetectionEngine
  File "backend/core/detector.py", line 4, in <module>
    import cv2
ModuleNotFoundError: No module named 'cv2'
```

### 2.3 根因定位

**两个问题同源，根因是：后端模块顶层存在对 `cv2` 的硬依赖导入，形成致命导入链。**

```
app.py 顶层 from api.health_api import health_bp
  → health_api: from core.engine import get_registry
    → engine.py: from core.detector import DetectionEngine   ← 模块级导入
      → detector.py: import cv2   ← 缺失 → ModuleNotFoundError
```

当运行环境的 `cv2` 缺失或损坏时，**整个 Flask 进程在 import 阶段崩溃、无法启动**。所有 `/api/*` 请求打到不存在的服务上，经 Vite 代理统一返回 **500**，导致：

- `GET /api/models` 无响应 → 前端 `fetchModels` 抛错 → 模型清单为空；
- `POST /api/models/load` 无响应 → 前端 `catch` 到 500 → 提示「注册不成功」。

**环境背景**：本机存在两个 Python 环境——Anaconda base（`opencv-python-headless 5.0.0.93` 安装损坏，包元数据存在但 `cv2` 模块文件缺失）与 `uav-vis` conda 环境（`cv2 4.13.0` 正常）。用 base 环境启动即触发崩溃。

**与设计意图矛盾**：README §环境要求明确声明"未安装 torch/ultralytics 时，系统仍可启动，模型管理/列表/mock 页面正常"。registry 本应仅依赖 PyYAML，却被 cv2 的导入链绑架，导致模型管理模块依赖了本应可选的推理依赖。

### 2.4 全量依赖扫描

除 `engine.py` 外，进一步扫描确认以下文件也在**模块顶层**导入 `cv2`/`numpy`：

| 文件 | 行号 | 用途 | 问题 |
|------|------|------|------|
| `backend/api/batches_api.py` | 9-10 | 架次预览占位图生成 | 模块级 `import cv2, numpy`，导致整个 mock API 失效 |
| `backend/api/processing_api.py` | 8-9 | 处理任务预览占位图生成 | 同上 |

（`detector.py`/`counter.py`/`clahe.py`/`tiling.py` 虽也导入 cv2，但它们本就只在检测/计数推理路径被调用，属可选项，只需从 `engine.py` 顶层移除即可。）

## 三、解决方案

遵循 README 的设计承诺，将 **模型管理与推理依赖（cv2/torch/ultralytics）解耦**，使后端在推理依赖缺失时仍能启动、模型管理/mock 页面正常工作，仅检测/计数降级。

### 3.1 `backend/core/engine.py`（核心修复）

将 `DetectionEngine` / `CountingEngine` 的导入从模块顶层移到 `init_engines()` 内部，并用独立 `try/except` 包裹：

```python
def init_engines():
    global registry, detector, counter, task_manager
    # ① 注册中心：仅依赖 PyYAML，必须成功
    registry = ModelRegistry(str(MODELS_YAML), lru_size=LRU_CACHE_SIZE)
    registry.load_from_yaml()
    # ② 任务管理器：仅依赖标准库
    task_manager = TaskManager(max_workers=MAX_WORKERS)
    # ③ 检测/计数引擎：依赖 cv2/numpy/ultralytics，缺失时降级
    try:
        from core.detector import DetectionEngine
        from core.counter import CountingEngine
        detector = DetectionEngine(registry)
        counter = CountingEngine(detector, task_manager)
    except Exception as exc:
        logger.warning(
            "检测/计数引擎初始化失败（推理功能不可用，模型管理正常）：%s", exc
        )
```

关键点：
- registry 与 task_manager 不依赖任何 cv2/torch，始终成功初始化；
- detector/counter 的导入延迟到函数内，异常时降级为 `None`；
- 各 API（detect/counting）已内置 `if detector is None` 的降级判断，返回 `success:False` 而非 500。

### 3.2 `backend/api/batches_api.py` 与 `processing_api.py`

两个 mock API 仅在生成预览占位图时用到 cv2/numpy，改为在 `_placeholder_image()` 内延迟导入，缺失时回退极简 JPEG：

```python
def _placeholder_image(label, w=400, h=300):
    try:
        import cv2
        import numpy as np
    except ImportError:
        return Response(b"\xff\xd8\xff\xe0\x00\x10JFIF", mimetype="image/jpeg")
    # ... 原有绘制逻辑
```

### 3.3 `backend/api/health_api.py`

修正 `detector_ready` 语义：原先错误地用 `registry.ready` 充当检测引擎就绪状态，现改为准确反映 `get_detector() is not None`：

```python
registry_ready = registry is not None and registry.ready
detector_ready = detector is not None
```

## 五、经验教训

1. **模块顶层导入需谨慎**：模块级 `import cv2` 会强制该模块在应用启动时就必须存在，把可选依赖变成硬依赖，导致整个服务不可用。凡"可选/可降级"的依赖（推理框架、GPU 库等），应延迟到使用点导入并 try/except 兜底。
2. **与设计文档对齐**：README 已声明"缺 torch/ultralytics 仍可启动模型管理"，实现却违背了该契约。修复后应回归验证设计承诺是否真正满足。
3. **环境差异是隐性炸弹**：本机 base 与 uav-vis 环境的 cv2 可用性不同，测试需明确指定目标环境，避免在错误环境上得出误导性结论。

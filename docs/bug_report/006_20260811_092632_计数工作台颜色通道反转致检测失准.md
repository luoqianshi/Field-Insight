# Bug 修复报告 #006

- **报告编号**：006
- **记录时间**：20260811_092632
- **问题标题**：计数工作台向 ultralytics 传入 RGB ndarray 致 R/B 通道反转，检测严重失准
- **涉及模块**：`backend/core/counter.py`、`backend/core/detector.py`、`backend/core/clahe.py`
- **严重程度**：高（计数工作台对所有图片检测结果均失准，核心功能不可用）
- **状态**：已修复并验证

---

## 一、问题现象

用户反馈：选用同一张图片（如 `.lqs/imgs/demo_text_imgs/DJI_20250511173415_0290_D_tile_0054_x0_y3316.jpg`），分别在【作物检测】工作台与【作物计数】工作台执行检测，计数工作台得到的检测结果严重失准，与检测工作台差异巨大。

实测数据（yolo12s-sugarcane，conf=0.25 iou=0.7 imgsz=640）：

| 工作台 | 检出数 |
|--------|--------|
| 作物检测（单次检测） | 14 |
| 作物计数（修复前） | 2（仅基准的 14%） |

## 二、排查过程

### 2.1 排除 CLAHE 与滑窗分块

对比 `.lqs/crop.py` 与项目实现，确认参数与算法逻辑一致，非失准原因：

| 维度 | `.lqs/crop.py` | 项目实现 | 结论 |
|------|----------------|----------|------|
| CLAHE clipLimit | 2.0 | `clahe.py` 2.0 | 一致 |
| CLAHE tileGridSize | (8,8) | (8,8) | 一致 |
| tile_size / overlap | 640 / 0.05 | 640 / 0.05 | 一致 |
| stride | 608 | 608 | 一致 |
| 边缘补块条件 | `w % stride != 0` | `starts[-1] != length-tile_size` | tiling.py 更健壮 |

滑窗分块 `tiling.py` 的边缘处理反而优于 `crop.py`，不会漏覆盖。

### 2.2 梳理两条调用链的颜色约定

**检测工作台（颜色正确 ✅）：**

```
Detect.vue → POST /api/detect (multipart 文件)
→ detect_api.py:80  detector.detect(tmp.name=文件路径, ...)
→ detector.py:27  engine.predict(image=文件路径字符串, ...)
→ ultralytics 内部 cv2.imread 读得 BGR → preprocess 转 RGB 喂模型 ✅
```

**计数工作台（修复前，颜色反转 ❌）：**

```
Counting.vue → POST /api/counting (multipart 文件)
→ counting_api.py:166  counter.count(tmp.name, ...)
→ counter.py:44-45  original = cv2.imread(path) → cv2.cvtColor(BGR2RGB)  # 转 RGB
→ counter.py:70  enhanced = clahe.enhance(RGB)
→ counter.py:73  tiles = tiling.slide_window(RGB 数组)
→ counter.py:221  detector.detect_batch([RGB_tile], ...)
→ detector.py:79  engine.predict(images=[RGB ndarray], batch=8, ...)
→ ultralytics 以为 ndarray 是 BGR → preprocess 做"BGR→RGB"(实为 RGB→BGR) → 模型看到颜色反转的图 ❌
```

### 2.3 根因定位

**ultralytics `YOLO.predict` 对 ndarray 输入默认按 BGR 处理**（与 `cv2.imread` 返回值约定一致），其内部 preprocess 会执行 BGR→RGB 转换后再喂给模型（模型训练时数据经由 BGR→RGB）。

- 检测工作台传**文件路径** → ultralytics 读 BGR → 转 RGB → 模型看到正确 RGB ✅
- 计数工作台（修复前）传 **RGB ndarray** → ultralytics 误以为是 BGR → 把 RGB 当 BGR 转换 → 模型实际看到 **BGR（R/B 通道反转）** ❌

甘蔗幼苗为绿色植物，R/B 反转后绿植呈品红色调，模型特征严重错位，导致大量漏检与误检。这完全解释了"同一张图检测工作台正常、计数工作台严重失准"的现象。

### 2.4 根因佐证（实测脚本）

对用户指定图片分别以三种方式调用 `engine.predict`：

```
图片: DJI_20250511173415_0290_D_tile_0054_x0_y3316.jpg
模型: yolo12s-sugarcane  (conf=0.25 iou=0.7 imgsz=640)
------------------------------------------------------------
文件路径 (检测工作台)    :   14 检出  [基准·正确]
BGR ndarray (修复后计数) :   14 检出  [应与基准一致]
RGB ndarray (修复前计数) :    2 检出  [颜色反转·失准]
============================================================
修复前后计数差异: 14 vs 2  (应明显回升)
```

结论：BGR ndarray 与文件路径结果完全一致（14=14），RGB ndarray 严重失准（2）。根因坐实。

## 三、解决方案

采用"统一为 BGR 全流程"方案：将 counter / clahe / detector 三者的颜色约定统一为 **BGR**（与 `cv2.imread`、`crop.py`、ultralytics ndarray 期望一致），从根因层消除通道错配。此方案同时让 `clahe.py` 与 `.lqs/crop.py` 在颜色空间上完全对齐。

### 改动 1：`backend/core/clahe.py`

LAB 转换颜色空间由 RGB 改为 BGR，与 `crop.py` 对齐：

```python
lab = cv2.cvtColor(image, cv2.COLOR_BGR2LAB)      # 原 RGB2LAB
lab[:, :, 0] = clahe.apply(lab[:, :, 0])
return cv2.cvtColor(lab, cv2.COLOR_LAB2BGR)        # 原 LAB2RGB
```

### 改动 2：`backend/core/counter.py`（删除 3 处多余转换）

- 加载原图：删除 `cv2.cvtColor(original, cv2.COLOR_BGR2RGB)`，保持 `cv2.imread` 返回的 BGR；
- 落盘子块：`tile_bgr = cv2.cvtColor(tile_img, cv2.COLOR_RGB2BGR)` → `tile_bgr = tile_img`（已是 BGR）；
- `_draw`：删除 `img = cv2.cvtColor(image, cv2.COLOR_RGB2BGR)`，改为 `img = image.copy()`。

### 改动 3：`backend/core/detector.py`

`_draw` ndarray 分支：`img = cv2.cvtColor(image, cv2.COLOR_RGB2BGR)` → `img = image.copy()`（假设 ndarray 为 BGR，与文件路径分支 `cv2.imread` 一致）。`detect` / `detect_batch` 本身不动——它们把 ndarray 原样传给 `engine.predict`，修复后均为 BGR，与 ultralytics 期望一致。

## 五、经验教训

1. **ultralytics ndarray 输入按 BGR 处理**：这是 ultralytics 长期稳定行为，`YOLO.predict` 接收 ndarray 时走与 `cv2.imread` 一致的 BGR 假设，内部再转 RGB 喂模型。任何向 `predict` 传 ndarray 的调用方必须保证 ndarray 为 BGR，否则颜色反转。
2. **颜色约定应在模块边界统一并显式声明**：本次 bug 的本质是 counter 内部约定 RGB、而 detector/ultralytics 约定 BGR，边界处未做归一化。正确做法是全流程统一为 cv2 原生 BGR，并在 `_draw` 等「像素→编码」节点保持一致，避免各模块各自转转换、互相假设。
3. **接口输入类型差异易引入隐性 bug**：检测工作台传文件路径、计数工作台传 ndarray，两条路径在 ultralytics 内部走不同的预处理分支，颜色处理语义不同。涉及多入口调用同一底层推理时，应确保输入归一化或在入口处显式标注约定。
4. **症状定位优先级**：当「同一模型同一图、两个入口结果差异大」时，应优先排查输入到 `predict` 的数据形态（路径 vs ndarray、颜色通道、尺寸），而非参数或后处理。

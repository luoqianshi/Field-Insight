## 一、需求背景

PRD v5 §1.7 中，模块二（数据处理）标记为 🔶 Mock 待实现——前端页面（Tasks.vue、TaskNew.vue、TaskDetail.vue）已创建完整 UI，但后端 `processing_api.py` 仅提供只读 Mock 接口（读取 `backend/mock/tasks.json` 返回占位数据），实际 CLAHE 增强与滑窗裁切逻辑未实现。

用户提出的核心需求：

1. **真实处理功能**：用真实功能替代 Mock，实现批量 CLAHE 增强（FR-P01）与批量滑窗裁切（FR-P02）。
2. **复用已有算法**：CLAHE 与滑窗裁切算法已在算法广场实现（`backend/core/clahe.py`、`backend/core/tiling.py`），后端应直接复用或做好兼容迭代。
3. **新增加工数据展示**：处理后的数据需要展示窗口，将处理数据管理拓展到【数据管理】部分，现有作为【原始数据】，学习【算法广场】的多导航栏窗口形式，新增【加工数据】栏目，从 output 目录获取处理后的数据信息（新功能，开发优先级放在最后）。

## 二、方案设计

### 2.1 后端架构：ProcessingEngine + ProcessingRegistry 双类

参考算法广场 `CountingEngine + ModelRegistry + task_manager` 的三段式架构，采用方案 A：

- **ProcessingEngine（执行层）**：无状态执行器，`run_clahe` / `run_crop` / `write_index` 三个公开方法，复用 `clahe.enhance` 与 `tiling.slide_window` 纯算法函数，叠加文件 IO 与进度回调。
- **ProcessingRegistry（持久化层）**：参考 `BatchRegistry` 模式，YAML 持久化任务记录（`data/processing_tasks.yaml`）+ 启动时自扫描 output/ 目录重建未注册任务。
- **独立任务队列**：新建 `processing_task_manager`（max_workers=1），与检测/计数队列隔离。

### 2.2 数据流

```
前端 POST 提交任务
  → processing_api 校验参数
  → registry.create_task() 写入 YAML（status=pending）生成 task_id
  → processing_task_manager.submit() 异步执行
  → ProcessingEngine.run_* 逐图读 → 算法 → 写 output/{task_id}/{sub_dir}/ → 进度回调
  → 进度回调实时更新 registry（progress/status）
  → 完成后写 index.json，registry 标记 completed
  → 前端轮询 GET /tasks/:id 获取进度
```

### 2.3 关键设计决策（经 brainstorming 澄清）

| 决策项 | 选择 | 说明 |
|--------|------|------|
| 任务持久化 | YAML 持久化 | `data/processing_tasks.yaml` |
| 多架次输出结构 | 按架次分子目录 | `output/{task_id}/{sub_dir}/*.jpg` |
| 子图命名规范 | `{orig_stem}_tile_{seq:04d}_x{ox}_y{oy}.jpg` | 采用项目 memory 规约，同步更新 PRD |
| 加工数据布局 | 双 tab | `/data/` 下加 DataSubTabs |
| 加工数据与任务关系 | 一一对应 | task_id 即 output 目录名 |
| 异步任务队列 | 独立队列 | 与检测/计数隔离 |
| 引擎降级 | cv2 缺失时返回 503 | 非 500 |

### 2.4 task_id 与目录名映射

- task_id 格式：`{task_type}_{ts}_{ms:03d}`，如 `clahe_20260812_153000_456`
- output 目录名与 task_id 完全一致，避免同秒创建冲突，可双向反查

**新增 [processing_engine.py](file:///d:/Data/New_Codes/Composite_Projects/UAV-Visual-Intelligence-System-in-Agriculture/backend/core/processing_engine.py)**

- `run_clahe(task_id, input_paths, params, output_dir, on_progress)`：遍历输入源 → `cv2.imread` 读 BGR → `clahe.enhance` → `cv2.imwrite` 保持原文件名，按输入源目录名分子目录输出

## 五、经验总结

1. **复用算法模块保持纯净**：ProcessingEngine 仅复用 `clahe.enhance` / `tiling.slide_window` 纯函数，不修改这两个文件，避免影响依赖它们的 `counter.py`。
2. **task_id 与目录名完全一致**：`{task_type}_{ts}_{ms:03d}` 格式避免同秒创建冲突，且 output 目录名即 task_id，可双向反查，简化加工数据与任务的一一对应。
3. **异步任务状态查询源**：任务状态始终从持久化层（registry）读取，task_manager 仅用于执行机制——保证重启后状态仍可查、前端轮询不受进程生命周期影响。
4. **测试隔离**：测试通过 monkeypatch `config.OUTPUT_DIR` + 在 `create_app()` 之后覆盖 engine 单例，避免污染真实 output/ 目录（create_app 内部会 init_engines 用默认路径重建单例）。
5. **.gitignore 陷阱**：`data/`（无前导斜杠）会匹配任意层级目录，误忽略 `frontend/src/views/data/`，必须用 `/data/` 锚定根目录。
6. **前端 TS 联合签名问题**：TaskNew 中 `submitClahe` 与 `submitCrop` 赋给同一变量会推断为交集类型导致参数不兼容，改用 if/else 分支分别调用。
7. **Windows 中文 commit 乱码**：PowerShell + git 下中文 commit message 会转码为 `?`，改用英文 message 或 UTF-8 存储保证可读性。

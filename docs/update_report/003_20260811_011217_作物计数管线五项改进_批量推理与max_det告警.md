## 一、需求背景

用户针对「作物计数」工作台（`/algo/counting`）提出五项改进需求，均与 [.lqs/qna_record/作物计数实现对比与改进分析报告.md](file:///d:/Data/New_Codes/Composite_Projects/UAV-Visual-Intelligence-System-in-Agriculture/.lqs/qna_record/作物计数实现对比与改进分析报告.md) 中识别的问题（§4.1-③、§4.3-⑥、§4.3-⑨）对应：

1. **max_det 参数定位确认与归位**：界面上 `max_det` 位于「CLAHE 分块检测」分组，语义不明。经代码核实，它是**单次检测（每个子块推理）参数**——`counter.py` 逐块调用 `detector.detect(tile, params=...)`，`max_det` 传入每块的 `engine.predict`，与整图无关。需求：将其移入单次检测（推理参数）分组，默认值改为 300。
2. **结果合并后的全局二次过滤**：conf 过滤原先仅发生在每块 `predict(conf=0.25)` 内部（报告 §4.1-③），映射合并后无全局闸门。需求：前端选项与后端操作均新增，默认值 0.5。
3. **子块检测结果日志**：不必实现子块落盘再检测（报告 §5 明确该项为参照项目劣化设计，不应引入），但要求保留每个子块检测的结果日志，全局计数在子块检测结果基础上进一步全局合并。
4. **批量分块推理**：原实现逐块串行调用 `engine.predict`（报告 §4.2-⑥），GPU 批处理完全闲置。需求：批量执行分块推理以提高性能。
5. **max_det 触顶告警**：密植场景若某块检出数达到 `max_det` 上限，低分框被静默丢弃且无任何提示（报告 §4.3-⑨）。需求：新增触顶告警，前端提示密植截断风险。

## 二、方案设计

### 2.1 max_det 归位与默认值对齐（需求 1）

- 语义确认：`max_det` 为单块检测上限（ultralytics `predict(max_det=...)` 逐块生效）。
- 前端：输入框从「CLAHE 分块检测」分组移入「计数参数」推理参数网格，标签改为 `max_det（单块上限）`，默认值 1000 → 300，与后端 detector 内置默认值及 `config/models.yaml` 各模型的 300 对齐。后端无需改动（`max_det` 本就在参数透传表中）。

### 2.2 全局 conf 二次过滤（需求 2）

- 落点遵循报告 P0-3 设计：在**全局合并（NMS）之后、编号之前**增加置信度闸门 `global_conf`（默认 0.5），过滤 `confidence < global_conf` 的检测；`global_conf <= 0` 视为关闭。
- 与每块内部 `conf`（默认 0.25，召回导向）分层：块内低阈值保召回，全局高阈值保精度，抑制低质量框进入最终计数。
- 结果新增 `filtered_count`（被二次过滤移除的数量），供追溯与导出。
- 参数链路：前端输入 → `_COUNTING_PARAM_TYPES` 类型转换 → `CountingEngine.count()` 生效。

### 2.3 子块结果日志与全局合并（需求 3）

- 保持内存直传（不引入子块落盘，避免 N 次磁盘 I/O 与 JPEG 有损压缩）。
- 每块检测后双通道留痕：
  - `logger.info` 输出块序号、偏移、检出数、是否触顶；
  - 累积结构化 `tile_results`：`{tile_index, offset_x, offset_y, det_count, max_det_reached}`，随结果落盘到 `counting_data.json`。
- 全局计数语义不变：子块检出 → 坐标映射回原图 → 全局 NMS 合并 → 二次过滤 → 编号统计。

### 2.4 批量分块推理（需求 4）

- `DetectionEngine` 新增 `detect_batch(images, ...)`：一次 `engine.predict(图像列表, batch=batch_size, ...)`，ultralytics 返回列表与输入顺序一一对应；复用既有 GPU→CPU 降级逻辑。
- `CountingEngine` 按 `batch_size`（默认 8，下限钳制 1）将 tiles 分批调用；批失败时回退为批内逐块串行 `detect`（块级容错，避免单批异常令整任务失败）。
- 进度回调仍按累计块数推进（`on_progress("detecting", done, total)`），`counting_api.py` 进度映射无需改动。
- 抽出 `_resolve_params` 统一参数解析（params > config > 内置默认），`detect` 与 `detect_batch` 共用。

### 2.5 max_det 触顶告警（需求 5）

- 触顶判据：单块检出数 `>=` 实际生效的 `max_det`（`detect`/`detect_batch` 返回值中透传 `max_det`）。
- 后端汇总 `max_det_reached_tiles`（触顶块索引列表）写入结果字典。
- 前端在「检测结果与计数标注」卡片内展示琥珀色告警条：触顶块数、max_det 上限值、块索引列表，并给出「调大 max_det 或调小 tile_size」的处置建议。
- 顺带修复报告 §4.3-⑩：`model_info` 改为通过 `self.detector.registry.get_config(model_name)` 直接获取，不再依赖最后一块检测结果的"便车"。

## 五、经验总结

1. **参数语义应与其 UI 分组一致**：`max_det` 误置于「分块检测」分组导致用户误以为是全局参数。涉及"单次推理 vs 全局流程"的参数应在 UI 分组上明确归位并加注（如「单块上限」），避免语义歧义。
2. **批量推理要配套容错回退**：ultralytics 列表批量推理可显著提速，但批失败（显存、解码异常等）代价大；「批优先 + 批内逐块回退」的两级策略以最小代价保住任务完整性。
3. **静默截断必须显性化**：`max_det` 截断属于不可察觉的漏计，后端只需在解析后比较 `len(dets) >= max_det` 即可产出告警数据，前端以告警条呈现处置建议——此类"上限类参数"都应考虑触顶提示。
4. **分层过滤优于单点过滤**：块内低 conf 保召回、合并后高 `global_conf` 保精度的两级设计，让用户可独立调优两个目标，比单纯调高块内 conf 更灵活。
5. **过程透明化降低异步任务疑虑**：异步任务下前端只见进度条，逐块日志 + 结构化 `tile_results`（随结果落盘）既便于排障，也让"确实逐块执行"可自证。
6. **Windows 环境下 pytest 需使用项目专用 conda 环境**（`~/.conda/envs/uav-vis/python.exe`），默认 Anaconda base 缺 cv2 会导致收集阶段 ImportError。
